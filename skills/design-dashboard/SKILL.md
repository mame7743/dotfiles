# ダッシュボード設計・レビュー

## 基本方針

利用者が何を判断し、次に何をするかから逆算する。データをすべて並べることを目的にしない。
最初に [出典と適用範囲](references/source.md) を読み、確認済みの公式情報とこのスキル独自の実務ルールを区別する。公式準拠・認証・全文反映を主張しない。
利用者の言語で説明する。既存の技術、デザインシステム、用語、権限を尊重する。

## 1. 要件を整理する

会話・提供ファイル・既存画面から分かる事項を先に整理する。不明点は判断を左右するものだけ簡潔に質問し、他は仮定として明記して進める。
- 目的：解きたい問題、見る人の問い、判断後の行動。
- 利用者：役割、知識、閲覧頻度、利用端末・場面。
- データ：対象、期間、粒度、出典、更新頻度、欠損、権限。
- 制約：実装環境、納期、画面サイズ、保守担当。

新規設計では「利用者／問い／判断・行動／必要な指標」の短い対応表を作る。レビューでは現状から推定し、確定情報と分ける。

## 2. 指標と情報を選ぶ

各要素を利用者の問いに対応させる。対応しない要素は削除候補か詳細画面に移す。
指標には名称、定義・式、単位、母集団、対象期間、集計粒度、比較基準、出典、更新時刻を定義する。不明な値や閾値を作らない。
実績・計画・予測を区別し、率は分母を、増減は比較期間を明示する。欠損をゼロに置き換えない。
サンプルデータを使う場合はサンプルであると表示する。

## 3. 骨格からプロトタイプを作る

内容と配置を先に決め、色や装飾を次に決める。主要な判断に必要な情報を先に置き、背景情報や明細を続ける。
[設計・点検ルール](references/design-review.md) を読み、各チャートの選択理由を説明できるようにする。
グリッド、余白、文字階層、色の意味、数値書式を共通化する。固定のカード数や画面比率を強制しない。
フィルターの適用範囲、現在条件、解除方法、詳細への導線を設計する。フィルター変更時の集計と見出しを一致させる。
提案依頼は要件・指標・配置案まで、実装依頼は利用可能な環境で動く成果物まで完成させる。既存画面のレビューは不要な全面再設計を避ける。

## 4. 実装して確かめる

依頼の実装環境に合わせる。特定のフロントエンドやチャートライブラリを勝手に必須にしない。
表示中の期間・単位・更新時刻を確認できるようにする。必要に応じて読み込み中、データなし、取得失敗、権限不足の状態を実装する。
実装・修正時は利用可能なプレビューで実際の描画を確認する。主要な利用幅と狭い幅で、文字切れ、横はみ出し、ラベル衝突、凡例、余白、操作を確認する。利用可能な手段がなければ未検証と報告する。
代表値で集計・率・フィルター結果を確かめる。配色だけで状態を判別させず、ラベルや記号を併用する。対話操作はキーボードとフォーカスも確認する。
ユーザー向け画面には開発説明や設計意図を詰め込まず、判断・操作に必要な文言を置く。

## 5. レビューと納品

レビューでは観察できた事実と推測を分ける。画像のみの場合、集計の正しさ、操作性、権限制御を検証済みとしない。
問題ごとに「箇所／観察事実／判断や操作への影響／具体的な修正／優先度」を示す。
優先度は、誤った判断・操作不能、理解や比較の阻害、見た目の改善の順。根拠のない総合点や公式合格判定を付けない。
納品時は成果物、主な変更、検証結果、残る不明点を簡潔に伝える。詳細仕様が求められない限り長い設計報告を付けない。
