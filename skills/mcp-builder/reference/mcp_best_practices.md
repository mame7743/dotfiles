# MCP サーバーのベストプラクティス

## クイックリファレンス

### サーバーの命名
- **Python**: `{service}_mcp`（例: `slack_mcp`）
- **Node/TypeScript**: `{service}-mcp-server`（例: `slack-mcp-server`）

### ツールの命名
- サービスプレフィックスを付けて snake_case を使用
- 形式: `{service}_{action}_{resource}`
- 例: `slack_send_message`、`github_create_issue`

### レスポンス形式
- JSON と Markdown の両方の形式をサポート
- JSON はプログラムによる処理用
- Markdown は人間が読みやすい形式用

### ページネーション
- 常に `limit` パラメータを尊重
- `has_more`、`next_offset`、`total_count` を返す
- デフォルトは20〜50件

### トランスポート
- **Streamable HTTP**: リモートサーバー、複数クライアントのシナリオ向け
- **stdio**: ローカル統合、コマンドラインツール向け
- SSE は避ける（streamable HTTP への置き換えにより非推奨）

---

## サーバーの命名規則

以下の標準化された命名パターンに従ってください:

**Python**: `{service}_mcp` 形式を使用（小文字とアンダースコア）
- 例: `slack_mcp`、`github_mcp`、`jira_mcp`

**Node/TypeScript**: `{service}-mcp-server` 形式を使用（小文字とハイフン）
- 例: `slack-mcp-server`、`github-mcp-server`、`jira-mcp-server`

名前は、汎用的で、統合するサービスを表し、タスクの説明から推測しやすく、バージョン番号を含まないものにしてください。

---

## ツールの命名と設計

### ツールの命名

1. **snake_case を使用**: `search_users`、`create_project`、`get_channel_info`
2. **サービスプレフィックスを含める**: あなたの MCP サーバーが他の MCP サーバーと一緒に使用される可能性を想定する
   - `send_message` ではなく `slack_send_message` を使用
   - `create_issue` ではなく `github_create_issue` を使用
3. **アクション指向にする**: 動詞（get、list、search、create など）で始める
4. **具体的にする**: 他のサーバーと競合する可能性のある汎用的な名前を避ける

### ツールの設計

- ツールの説明は、機能を狭く明確に説明する必要がある
- 説明は実際の機能と正確に一致させる必要がある
- ツールのアノテーションを提供する (readOnlyHint、destructiveHint、idempotentHint、openWorldHint)
- ツールの操作は焦点を絞り、アトミックに保つ

---

## レスポンス形式

データを返すすべてのツールは、複数の形式をサポートする必要があります:

### JSON 形式（`response_format="json"`）
- 機械可読な構造化データ
- 利用可能なすべてのフィールドとメタデータを含める
- 一貫したフィールド名と型
- プログラムによる処理に使用

### Markdown 形式（`response_format="markdown"`、通常はデフォルト）
- 人間が読みやすい整形されたテキスト
- 見出し、リスト、書式を使用して明確にする
- タイムスタンプを人間が読みやすい形式に変換
- 表示名と ID を括弧付きで表示
- 冗長なメタデータは省略

---

## ページネーション

リソースを一覧表示するツール向け:

- **常に `limit` パラメータを尊重する**
- **ページネーションを実装する**: `offset` またはカーソルベースのページネーションを使用
- **ページネーションのメタデータを返す**: `has_more`、`next_offset`/`next_cursor`、`total_count` を含める
- **すべての結果をメモリに読み込まない**: 大規模なデータセットでは特に重要
- **妥当な制限をデフォルトにする**: 20〜50件が一般的

ページネーションレスポンスの例:
```json
{
  "total": 150,
  "count": 20,
  "offset": 0,
  "items": [...],
  "has_more": true,
  "next_offset": 20
}
```

## トランスポートのオプション

### Streamable HTTP

**最適な用途**: リモートサーバー、ウェブサービス、複数クライアントのシナリオ

**特徴**:
- HTTP を介した双方向通信
- 複数の同時クライアントをサポート
- ウェブサービスとしてデプロイ可能
- サーバーからクライアントへの通知が可能

**使用する場合**:
- 複数のクライアントに同時にサービスを提供する場合
- クラウドサービスとしてデプロイする場合
- ウェブアプリケーションとの統合

### stdio

**最適な用途**: ローカル統合、コマンドラインツール

**特徴**:
- 標準入出力ストリームでの通信
- セットアップが簡単で、ネットワーク設定が不要
- クライアントのサブプロセスとして実行

**使用する場合**:
- ローカル開発環境向けのツールを構築する場合
- デスクトップアプリケーションと統合する場合
- 単一ユーザー、単一セッションのシナリオ

**注意**: stdio サーバーは stdout にログを出力しないでください（ログには stderr を使用）

### トランスポートの選定

| 基準 | stdio | Streamable HTTP |
|-----------|-------|-----------------|
| **デプロイ** | ローカル | リモート |
| **クライアント** | 単一 | 複数 |
| **複雑さ** | 低 | 中 |
| **リアルタイム** | なし | あり |

## セキュリティのベストプラクティス

### 認証と認可

**OAuth 2.1**:
- 認められた認証局からの証明書を使用した安全な OAuth 2.1 を使用
- リクエストを処理する前にアクセストークンを検証
- サーバー専用に発行されたトークンのみを受け入れる

**API キー**:
- API キーはコードではなく環境変数に保存
- サーバー起動時にキーを検証
- 認証に失敗した場合は明確なエラーメッセージを提供

### 入力検証

- ディレクトリトラバーサルを防ぐためにファイルパスをサニタイズ
- URL と外部識別子を検証
- パラメータのサイズと範囲をチェック
- システムコールでのコマンドインジェクションを防止
- すべての入力にスキーマ検証 (Pydantic/Zod) を使用

### エラーハンドリング

- 内部エラーをクライアントに公開しない
- セキュリティ関連のエラーはサーバー側でログに記録
- 有益だが内部情報を漏らさないエラーメッセージを提供
- エラー発生後はリソースをクリーンアップ

### DNS リバインディング対策

ローカルで実行する streamable HTTP サーバー向け:
- DNS リバインディング保護を有効化
- すべての着信接続で `Origin` ヘッダーを検証
- `0.0.0.0` ではなく `127.0.0.1` にバインド

## ツールのアノテーション

クライアントがツールの動作を理解できるようにアノテーションを提供します:

| アノテーション | 型 | デフォルト | 説明 |
|-----------|------|---------|-------------|
| `readOnlyHint` | boolean | false | ツールが環境を変更しないことを示す |
| `destructiveHint` | boolean | true | ツールが破壊的な更新を行う可能性があることを示す |
| `idempotentHint` | boolean | false | 同じ引数で繰り返し呼び出しても追加の効果がないことを示す |
| `openWorldHint` | boolean | true | ツールが外部エンティティと相互作用することを示す |

**重要**: アノテーションはヒントであり、セキュリティを保証するものではありません。クライアントはアノテーションのみに基づいてセキュリティ上重要な決定を下すべきではありません。

---

## エラーハンドリング

- 標準の JSON-RPC エラーコードを使用
- ツールのエラーは結果オブジェクト内で報告（プロトコルレベルのエラーは不可）
- 有益で具体的なエラーメッセージと、次のステップの提案を提供
- 内部実装の詳細を公開しない
- エラー時にリソースを適切にクリーンアップ

エラーハンドリングの例:
```typescript
try {
  const result = performOperation();
  return { content: [{ type: "text", text: result }] };
} catch (error) {
  return {
    isError: true,
    content: [{
      type: "text",
      text: `Error: ${error.message}. Try using filter='active_only' to reduce results.`
    }]
  };
}
```

## テスト要件

包括的なテストは以下をカバーする必要があります:

- **機能テスト**: 有効・無効な入力で正しく実行されるかを検証
- **統合テスト**: 外部システムとの連携をテスト
- **セキュリティテスト**: 認証、入力サニタイズ、レート制限を検証
- **パフォーマンステスト**: 負荷時とタイムアウト時の動作を確認
- **エラーハンドリング**: 適切なエラー報告とクリーンアップを確認

---

## ドキュメント要件

- すべてのツールと機能の明確なドキュメントを提供
- 動作例を含める（主要機能ごとに最低3つ）
- セキュリティ上の考慮事項を文書化
- 必要な権限とアクセスレベルを指定
- レート制限とパフォーマンス特性を文書化
