# Skill Creator

スキルの新規作成と反復的な改善を行うためのスキルです。

高レベルで見ると、スキル作成のプロセスは次のような流れになります:

- スキルに何をさせるのか、そしておおまかにどのように実現するかを決める
- スキルのドラフトを書く
- いくつかのテストプロンプトを作成し、スキルへのアクセス権を持つ claude でそれらを実行する
- 結果を定性的・定量的の両面でユーザーが評価できるよう支援する
  - 実行がバックグラウンドで進行している間に、定量的な evals がない場合はいくつかドラフトを作成する（既存のものがある場合は、そのまま使うか、変更が必要だと感じたら変更する）。その後、それらをユーザーに説明する（既に存在する場合は、既存のものを説明する）
  - `eval-viewer/generate_review.py` スクリプトを使って結果をユーザーが見られるように表示し、定量的なメトリクスも確認してもらう
- ユーザーによる結果の評価からのフィードバックに基づいてスキルを書き直す（定量的なベンチマークから明らかになった重大な欠陥がある場合も同様）
- 満足できるまで繰り返す
- テストセットを拡張し、より大規模に再試行する

このスキルを使うときのあなたの仕事は、ユーザーがこのプロセスのどこにいるのかを把握し、その段階を進むのを支援することです。例えば、ユーザーが「Xのためのスキルを作りたい」と言ったら、その意味を絞り込む手助けをし、ドラフトを書き、テストケースを書き、評価方法を決め、すべてのプロンプトを実行し、それを繰り返します。

一方、ユーザーがすでにスキルのドラフトを持っている場合もあります。その場合は、ループの eval / 反復パートに直接進むことができます。

もちろん、常に柔軟であるべきです。ユーザーが「一連の評価を実行する必要はないよ、一緒に進めてくれ」と言った場合は、そうすることもできます。

そして、スキルが完成した後（ただし繰り返しますが、順序は柔軟です）、スキルのトリガリングを最適化するための専用スクリプトである description 改善ツールも実行できます。

いいですね。

## ユーザーとのコミュニケーション

スキルクリエイターは、コーディング用語に精通している度合いが大きく異なる人々に使われる可能性があります。まだ聞いたことがないかもしれませんが（最近始まったばかりなので当然ですが）、現在はClaudeの力に刺激されて、配管工がターミナルを開いたり、親や祖父母が「npmのインストール方法」をググったりするようなトレンドがあります。一方で、ユーザーの大多数はおそらくコンピュータにかなり精通しています。

ですから、コミュニケーションの言葉遣いを決めるために、コンテキストの手がかりに注意してください。デフォルトの場合の目安としては:

- "evaluation" と "benchmark" はぎりぎりですが許容範囲
- "JSON" と "assertion" については、説明なしで使う前に、ユーザーがそれらを知っているという確かな手がかりを確認してください

迷ったら用語を簡単に説明しても構いませんし、ユーザーが理解できるか自信がない場合は、短い定義を添えて明確にしてもかまいません。

## スキルの作成

### 意図の把握

まず、ユーザーの意図を理解することから始めます。現在の会話には、ユーザーがスキルとして取り込みたいワークフローがすでに含まれているかもしれません（例:「これをスキルにして」など）。その場合は、まず会話履歴から答えを抽出します — 使用されたツール、ステップの順序、ユーザーが行った修正、観察された入力・出力形式など。不足している部分はユーザーに埋めてもらう必要があるかもしれませんので、次のステップに進む前に確認してください。

1. このスキルによってClaudeに何ができるようになるべきか?
2. このスキルはいつトリガーされるべきか?（どのようなユーザーのフレーズ・コンテキストか）
3. 期待される出力形式は何か?
4. スキルが機能することを確認するためのテストケースを設定すべきか? 客観的に検証可能な出力を持つスキル（ファイル変換、データ抽出、コード生成、固定されたワークフローのステップ）はテストケースの恩恵を受けます。主観的な出力を持つスキル（文体、アートなど）には通常必要ありません。スキルの種類に基づいて適切なデフォルトを提案しますが、決定はユーザーに委ねてください。

### ヒアリングとリサーチ

エッジケース、入力・出力形式、サンプルファイル、成功基準、依存関係について積極的に質問してください。テストプロンプトを書くのは、この部分が固まるまで待ちましょう。

利用可能な MCP を確認してください。リサーチに役立つ場合（ドキュメントの検索、類似スキルの発見、ベストプラクティスの調査など）は、可能ならサブエージェントを使って並行してリサーチし、それができない場合はインラインで行ってください。ユーザーの負担を減らすために、コンテキストを持って臨んでください。

### SKILL.md の作成

ユーザーへのヒアリングに基づいて、以下の構成要素を埋めていきます:

- **name**: スキルの識別子
- **description**: いつトリガーされるか、何をするか。これは主要なトリガー機構です — スキルが何をするかと、いつ使うべきかという具体的なコンテキストの両方を含めてください。「いつ使うか」の情報はすべてここに入れ、本文には入れないでください。注: 現在のClaudeはスキルを「過少トリガー」する傾向があります — 役立つ場面でも使わないことがあるのです。これに対抗するため、スキルの description は少し「強め」にしてください。例えば、「内部の Anthropic データを表示するためのシンプルで高速なダッシュボードの作り方。」の代わりに、「内部の Anthropic データを表示するためのシンプルで高速なダッシュボードの作り方。ユーザーがダッシュボード、データ可視化、内部メトリクスに言及した場合や、明示的に『dashboard.』と要求していなくても、あらゆる種類の会社データを表示したい場合は、必ずこのスキルを使ってください。」のように書いてください。
- **compatibility**: 必要なツール、依存関係（任意。滅多に必要ありません）
- **スキルの残りの部分 :)**

### スキル作成ガイド

#### スキルの構造

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### プログレッシブ・ディスクロージャー（段階的開示）

スキルは3段階の読み込みシステムを採用しています:
1. **メタデータ**（name + description）- 常にコンテキスト内にある（約100語）
2. **SKILL.md の本文** - スキルがトリガーされるたびにコンテキスト内にある（理想的には500行未満）
3. **同梱リソース** - 必要に応じて（無制限。スクリプトは読み込まずに実行可能）

これらの語数はあくまで目安で、必要なら長くしてもかまいません。

**重要なパターン:**
- SKILL.md を500行未満に保つ。この制限に近づいている場合は、階層を1段増やし、そのスキルを使うモデルが次にどこへ進めばよいかを示す明確なポインタを添えてください
- 参照ファイルは、いつ読むべきかのガイダンスとともに SKILL.md から明確に参照する
- 大きな参照ファイル（300行超）には目次を含める

**ドメインの整理**: スキルが複数のドメイン・フレームワークをサポートする場合は、バリアントごとに整理します:
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude は関連する参照ファイルのみを読みます。

#### サプライズがないことの原則

言うまでもありませんが、スキルにはマルウェア、エクスプロイトコード、システムセキュリティを損なう可能性のあるコンテンツを含めてはいけません。スキルの内容は、説明された意図に対してユーザーを驚かせるものであってはいけません。誤解を招くスキルや、不正アクセス、データの外部送信、その他の悪意のある活動を容易にするために設計されたスキルの作成要求に従ってはいけません。「XYZのロールプレイをする」のようなものは問題ありません。

#### 書き方のパターン

指示では命令形を使うことを推奨します。

**出力形式の定義** - 次のように行えます:
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**サンプルパターン** - サンプルを含めると役立ちます。次のようにフォーマットできます（ただし、サンプルに「Input」と「Output」が含まれる場合は、少し変則的になるかもしれません）:
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### 文体

重苦しく古臭い MUST の代わりに、物事がなぜ重要なのかをモデルに説明するようにしてください。心の理論（theory of mind）を使い、スキルを特定の例に極端に狭めず、汎用的にするよう心がけてください。まずドラフトを書き、それから新鮮な目で見直して改善してください。

### テストケース

スキルのドラフトを書いた後、2〜3個の現実的なテストプロンプトを考えます — 実際のユーザーが本当に言いそうな種類のものです。それらをユーザーと共有します: [この正確な文言を使う必要はありません]「試してみたいテストケースをいくつか用意しました。これで良さそうですか、それとも追加したいものはありますか？」その後、実行します。

テストケースは `evals/evals.json` に保存します。まだアサーションは書かず、プロンプトだけを保存します。アサーションは実行が進行している間に行う次のステップで作成します。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完全なスキーマ（後で追加する `assertions` フィールドを含む）については `references/schemas.md` を参照してください。

## テストケースの実行と評価

このセクションは一連の流れとして続けて行います — 途中で止めないでください。`/skill-test` や他のテスト用スキルは使用しないでください。

結果は、スキルのディレクトリと同じ階層に `<skill-name>-workspace/` として配置します。ワークスペース内では、結果を反復ごとに整理します（`iteration-1/`、`iteration-2/` など）。その中で、各テストケースはディレクトリを1つ持ちます（`eval-0/`、`eval-1/` など）。これらをあらかじめすべて作成せず、進みながら必要なディレクトリだけを作成してください。

### ステップ1: すべての実行（with-skill と baseline の両方）を同じターンで開始する

各テストケースについて、同じターンで2つのサブエージェントを起動します — 1つはスキルあり、もう1つはスキルなしです。これは重要です: 先に with-skill の実行を開始して、後で baseline に戻るということはしないでください。すべてを一度に起動し、ほぼ同時に終了するようにします。

**With-skill 実行:**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 実行**（同じプロンプトですが、baseline はコンテキストに依存します）:
- **新規スキルの作成**: スキルなし。同じプロンプト、スキルのパスなし、保存先は `without_skill/outputs/`。
- **既存スキルの改善**: 古いバージョン。編集前にスキルをスナップショットします（`cp -r <skill-path> <workspace>/skill-snapshot/`）。その後、baseline サブエージェントをスナップショットに向けます。保存先は `old_skill/outputs/`。

各テストケースに対して `eval_metadata.json` を書きます（アサーションは今のところ空でかまいません）。各 eval には、テストしている内容に基づいた説明的な名前を付けます — 単なる「eval-0」ではなく。この名前はディレクトリ名にも使います。この反復で新しい、または変更された eval プロンプトを使う場合は、各新しい eval ディレクトリにこれらのファイルを作成してください — 前回の反復から引き継がれると想定しないでください。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### ステップ2: 実行が進行している間にアサーションを作成する

実行が終わるのをただ待つのではなく、この時間を生産的に使いましょう。各テストケースの定量的なアサーションを作成し、ユーザーに説明します。アサーションが `evals/evals.json` にすでに存在する場合は、それを確認し、何をチェックしているのかを説明します。

良いアサーションは客観的に検証可能で、説明的な名前を持ちます — ベンチマークビューアーで結果を一目見ただけで、それぞれが何をチェックしているかすぐに理解できるように読める必要があります。主観的なスキル（文体、デザイン品質など）は定性的に評価する方が適しています — 人間の判断が必要なものにアサーションを無理に押し付けないでください。

作成したら、`eval_metadata.json` ファイルと `evals/evals.json` をアサーションで更新します。また、ビューアーで何が見えるか（定性的な出力と定量的なベンチマークの両方）もユーザーに説明します。

### ステップ3: 実行完了時にタイミングデータを取得する

各サブエージェントのタスクが完了すると、`total_tokens` と `duration_ms` を含む通知を受け取ります。このデータをすぐに、実行ディレクトリ内の `timing.json` に保存してください:

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

このデータを取得できるのはこの機会だけです — タスク通知を通じて届き、他の場所には保存されません。一括処理しようとせず、各通知が届き次第処理してください。

### ステップ4: 採点・集計・ビューアーの起動

すべての実行が完了したら:

1. **各実行を採点する** — grader サブエージェントを起動し（またはインラインで採点し）、`agents/grader.md` を読んで、各アサーションを出力に対して評価させます。結果は各実行ディレクトリ内の `grading.json` に保存します。grading.json の expectations 配列は `text`、`passed`、`evidence` というフィールド名を使わなければなりません（`name`/`met`/`details` やその他のバリアントではダメです）— ビューアーはこれらの正確なフィールド名に依存しています。プログラムでチェックできるアサーションについては、目視ではなくスクリプトを書いて実行してください — スクリプトはより速く、信頼性が高く、反復をまたいで再利用できます。

2. **ベンチマークに集計する** — skill-creator ディレクトリから集計スクリプトを実行します:
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   これにより、各構成の pass_rate、time、tokens を含む `benchmark.json` と `benchmark.md` が生成されます（平均±標準偏差とデルタ付き）。benchmark.json を手動で生成する場合は、ビューアーが期待する正確なスキーマについて `references/schemas.md` を参照してください。
   各 with_skill バージョンを、対応する baseline の前に置いてください。

3. **アナリストパスを行う** — ベンチマークデータを読み、集計統計が隠してしまうパターンを明らかにします。探すべきもの（スキルに関係なく常に合格するアサーション（判別力がないもの）、分散が大きい evals（フレークの可能性）、時間・トークンのトレードオフなど）については `agents/analyzer.md`（「ベンチマーク結果の分析」セクション）を参照してください。

4. **定性的な出力と定量的なデータの両方を使ってビューアーを起動する**:
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   反復2以降では、`--previous-workspace <workspace>/iteration-<N-1>` も渡してください。

   **Cowork / ヘッドレス環境:** `webbrowser.open()` が使えない場合や、環境にディスプレイがない場合は、サーバーを起動する代わりに `--static <output_path>` を使ってスタンドアロンの HTML ファイルを書き出してください。フィードバックは、ユーザーが「Submit All Reviews」をクリックすると `feedback.json` ファイルとしてダウンロードされます。ダウンロード後、次の反復で拾えるように `feedback.json` をワークスペースディレクトリにコピーしてください。

注: ビューアーの作成には `generate_review.py` を使用してください。カスタム HTML を書く必要はありません。

5. **ユーザーに次のように伝える** — 例:「ブラウザで結果を開きました。タブが2つあります — 「Outputs」では各テストケースをクリックしてフィードバックを残せます。「Benchmark」は定量的な比較を示します。確認が終わったら、ここに戻って教えてください。」

### ユーザーがビューアーで見るもの

「Outputs」タブでは、一度に1つのテストケースが表示されます:
- **Prompt**: 与えられたタスク
- **Output**: スキルが生成したファイル（可能な場合はインラインで表示）
- **Previous Output**（反復2以降）: 前回の反復の出力を示す折りたたみセクション
- **Formal Grades**（採点が実行された場合）: アサーションの合格・不合格を示す折りたたみセクション
- **Feedback**: 入力中に自動保存されるテキストボックス
- **Previous Feedback**（反復2以降）: 前回のコメント（テキストボックスの下に表示）

「Benchmark」タブには統計のサマリーが表示されます: 各構成の合格率、タイミング、トークン使用量、および eval ごとの内訳とアナリストの所見です。

ナビゲーションは前後ボタンまたは矢印キーで行います。終了したら「Submit All Reviews」をクリックすると、すべてのフィードバックが `feedback.json` に保存されます。

### ステップ5: フィードバックを読む

ユーザーが終わったと伝えてきたら、`feedback.json` を読みます:

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空のフィードバックは、ユーザーが問題ないと判断したことを意味します。ユーザーが具体的な不満を挙げたテストケースに改善の焦点を当ててください。

使い終わったらビューアーサーバーを停止します:

```bash
kill $VIEWER_PID 2>/dev/null
```

## スキルの改善

これはループの核心です。テストケースを実行し、ユーザーが結果を確認し、そのフィードバックに基づいてスキルをより良くする必要があります。

### 改善の考え方

1. **フィードバックから一般化する。** ここで起きている大きな絵は、私たちが何百万回（文字通りかもしれないし、それ以上かもしれない）さまざまなプロンプトで使えるスキルを作ろうとしているということです。ここであなたとユーザーは、より速く進むためにほんの数個のサンプルを繰り返し反復しています。ユーザーはこれらのサンプルを熟知しており、新しい出力を素早く評価できます。しかし、あなたとユーザーが共同開発しているスキルがそれらのサンプルだけでしか機能しないなら、それは役に立ちません。細かい過学習的な変更や、抑圧的に制限的な MUST を入れるのではなく、しつこい問題がある場合は、別のメタファーに枝分かれしてみたり、異なる作業パターンを推奨してみたりしてください。試すのは比較的安価で、素晴らしいものが見つかるかもしれません。

2. **プロンプトを引き締める。** 機能していないものを取り除きます。最終出力だけでなく、必ずトランスクリプトも読んでください — スキルがモデルに非生産的なことをたくさんさせて時間を無駄にしているように見えるなら、その原因となっているスキルの部分を削除して、何が起きるか試してみてください。

3. **理由（なぜ）を説明する。** モデルに求めているすべてのことの背後にある「なぜ」を一生懸命説明してください。今日のLLMは*賢い*です。優れた心の理論を持ち、良いハーネスを与えられれば、機械的な指示を超えて本当に物事を実現できます。ユーザーのフィードバックが素っ気なかったり苛立っていたりしても、タスクと、ユーザーがなぜそのように書いたのか、実際に何を書いたのかを本当に理解するよう努め、その理解を指示に伝えてください。ALWAYS や NEVER を大文字で書いている自分に気づいたら、それは黄色信号です — 可能であれば、枠組みを変えて、あなたが求めていることがなぜ重要なのかをモデルが理解できるように説明してください。それがより人間的で、強力で、効果的なアプローチです。

4. **テストケース全体で繰り返される作業を探す。** テスト実行のトランスクリプトを読み、サブエージェントがそれぞれ独立に似たようなヘルパースクリプトを書いたり、同じ多段階のアプローチを取ったりしていないか確認してください。3つのテストケースすべてでサブエージェントが `create_docx.py` や `build_chart.py` を書いていたなら、それはスキルがそのスクリプトを同梱すべき強いシグナルです。一度書いて `scripts/` に置き、スキルにそれを使うよう指示してください。これにより、将来のすべての呼び出しが車輪の再発明をしなくて済みます。

このタスクはかなり重要です（ここでは年間数十億ドルの経済的価値を生み出そうとしているのです！）。あなたの考える時間はボトルネックではありません。時間をかけて、じっくり熟考してください。改訂ドラフトを書き、それを新たに見直して改善することをお勧めします。ユーザーの頭の中に入り込み、彼らが何を求め、何を必要としているかを本当に理解するよう最善を尽くしてください。

### 反復ループ

スキルを改善した後:

1. 改善内容をスキルに適用する
2. baseline 実行を含むすべてのテストケースを、新しい `iteration-<N+1>/` ディレクトリで再実行する。新規スキルを作成している場合、baseline は常に `without_skill`（スキルなし）で、それは反復をまたいで同じままです。既存スキルを改善している場合は、何が baseline として理にかなうかを判断してください: ユーザーが持ち込んだ元のバージョンか、前回の反復か。
3. 前回の反復を指す `--previous-workspace` を指定してレビューアーを起動する
4. ユーザーがレビューして終了したと伝えてくるのを待つ
5. 新しいフィードバックを読み、さらに改善し、繰り返す

次のいずれかになるまで続けます:
- ユーザーが満足したと言う
- フィードバックがすべて空である（すべて問題ない）
- 意味のある進歩がなくなっている

## 上級: ブラインド比較

スキルの2つのバージョンをより厳密に比較したい状況（例: ユーザーが「新しいバージョンは本当に良いの?」と尋ねる場合）には、ブラインド比較システムがあります。詳細は `agents/comparator.md` と `agents/analyzer.md` を読んでください。基本的な考え方は: 2つの出力を、どちらがどちらかを伝えずに独立したエージェントに渡し、品質を判断させる。そして、勝者がなぜ勝ったのかを分析する、というものです。

これは任意で、サブエージェントが必要で、ほとんどのユーザーは必要としません。人間によるレビューループで通常は十分です。

## description の最適化

SKILL.md の frontmatter にある description フィールドは、Claude がスキルを呼び出すかどうかを決定する主要な機構です。スキルを作成・改善した後は、トリガー精度を向上させるために description の最適化を提案してください。

### ステップ1: トリガー eval クエリの生成

20個の eval クエリを作成します — トリガーすべきものとトリガーすべきでないものを混ぜます。JSONとして保存します:

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

クエリは現実的で、Claude Code や Claude.ai のユーザーが実際に入力するようなものでなければなりません。抽象的な要求ではなく、具体的で特定の、十分な詳細を含む要求です。例えば、ファイルパス、ユーザーの仕事や状況に関する個人的な文脈、列名や値、会社名、URLなど。少しの背景ストーリーも。一部は小文字だったり、略語、タイプミス、カジュアルな話し方を含んでいてもかまいません。さまざまな長さを混ぜ、明確に線引きできるものではなくエッジケースに焦点を当ててください（ユーザーに承認してもらう機会があります）。

Bad: `"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

Good: 「おっと、上司がこの xlsx ファイルを送ってきたんだけど（ダウンロードフォルダにあって、『Q4 sales final FINAL v2.xlsx』みたいな名前）、利益率をパーセンテージで表示する列を追加してほしいって。売上は C 列、コストは D 列だと思う」

**should-trigger** クエリ（8〜10個）については、カバレッジを考えてください。同じ意図の異なる言い回しが必要です — フォーマルなものも、カジュアルなものも。ユーザーがスキル名やファイルタイプを明示的に挙げていないが、明らかにそれを必要としているケースを含めます。あまり一般的でない使用例や、このスキルが別のスキルと競合するが勝つべきケースもいくつか混ぜてください。

**should-not-trigger** クエリ（8〜10個）については、最も価値があるのはニアミスです — スキルとキーワードや概念を共有しているが、実際には別のものを必要とするクエリです。隣接ドメイン、単純なキーワード一致ならトリガーするがそうすべきではない曖昧な言い回し、クエリがスキルの機能に触れているが別のツールの方が適切なコンテキスト、といったケースを考えてください。

避けるべき重要なこと: should-not-trigger クエリを明らかに無関係にしないこと。PDFスキルに対するネガティブテストとして「フィボナッチ関数を書いて」は簡単すぎます — 何もテストしていません。ネガティブケースは本当に厄介なものにするべきです。

### ステップ2: ユーザーとの確認

HTMLテンプレートを使って eval セットをユーザーに提示して確認してもらいます:

1. `assets/eval_review.html` からテンプレートを読む
2. プレースホルダーを置き換える:
   - `__EVAL_DATA_PLACEHOLDER__` → eval アイテムの JSON 配列（周りに引用符は付けない — JS の変数代入です）
   - `__SKILL_NAME_PLACEHOLDER__` → スキルの名前
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → スキルの現在の description
3. 一時ファイルに書き出し（例: `/tmp/eval_review_<skill-name>.html`）、開く: `open /tmp/eval_review_<skill-name>.html`
4. ユーザーはクエリを編集し、should-trigger を切り替え、エントリを追加・削除してから、「Export Eval Set」をクリックできる
5. ファイルは `~/Downloads/eval_set.json` にダウンロードされる — 複数ある場合に備えて、Downloads フォルダの最新バージョンを確認してください（例: `eval_set (1).json`）

このステップは重要です — 悪い eval クエリは悪い description につながります。

### ステップ3: 最適化ループの実行

ユーザーに伝えます:「時間がかかります — バックグラウンドで最適化ループを実行して、定期的に確認します。」

eval セットをワークスペースに保存し、バックグラウンドで実行します:

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

システムプロンプトのモデルID（現在のセッションを動かしているもの）を使って、トリガリングテストがユーザーが実際に体験するものと一致するようにします。

実行中は、定期的に出力を tail して、どの反復にいるのか、スコアがどうなっているのかをユーザーに伝えます。

これにより、最適化ループ全体が自動的に処理されます。eval セットを60%のトレインと40%の保留テストに分割し、現在の description を評価し（各クエリを3回実行して信頼できるトリガー率を得る）、失敗したものに基づいて改善案を Claude に提案させます。各新しい description をトレインとテストの両方で再評価し、最大5回反復します。完了すると、反復ごとの結果を示す HTML レポートをブラウザで開き、`best_description` を含む JSON を返します — 過学習を避けるため、トレインスコアではなくテストスコアで選択されます。

### スキルトリガーの仕組み

トリガー機構を理解すると、より良い eval クエリを設計できます。スキルは、名前と description とともに Claude の `available_skills` リストに表示され、Claude はその description に基づいてスキルを参照するかどうかを決定します。重要なのは、Claude は簡単に自分で処理できるタスクではスキルを参照しないということです — 「このPDFを読んで」のような単純な一段階のクエリは、description が完全に一致していてもスキルをトリガーしないかもしれません。なぜなら Claude は基本ツールで直接処理できるからです。複雑で多段階の、または専門的なクエリは、description が一致すれば確実にスキルをトリガーします。

つまり、eval クエリは、Claude がスキルを参照することで実際に恩恵を受けるほど十分に実質的なものでなければなりません。「ファイルXを読んで」のような単純なクエリは悪いテストケースです — description の品質に関係なくスキルをトリガーしません。

### ステップ4: 結果の適用

JSON 出力から `best_description` を取り出し、スキルの SKILL.md frontmatter を更新します。ユーザーに変更前・変更後を見せ、スコアを報告します。

### パッケージ化と提示（`present_files` ツールが利用可能な場合のみ）

`present_files` ツールにアクセスできるか確認してください。できない場合はこのステップをスキップします。できる場合は、スキルをパッケージ化し、.skill ファイルをユーザーに提示します:

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

パッケージ化後、結果の `.skill` ファイルのパスをユーザーに案内してインストールできるようにします。

## Claude.ai 固有の指示

Claude.ai では、コアワークフローは同じです（ドラフト → テスト → レビュー → 改善 → 繰り返し）が、Claude.ai にはサブエージェントがないため、一部の仕組みが変わります。適応させるべき点は次のとおりです:

**テストケースの実行**: サブエージェントがないということは並列実行ができないということです。各テストケースについて、スキルの SKILL.md を読み、その指示に従ってテストプロンプトを自分で達成してください。一度に1つずつ行います。これは独立したサブエージェントより厳密さに欠けます（自分でスキルを書いた上に自分で実行するので、完全なコンテキストを持っています）が、有用な健全性チェックになります — そして人間によるレビューステップが補ってくれます。baseline 実行はスキップし、スキルを使って要求どおりにタスクを完了するだけにしてください。

**結果のレビュー**: ブラウザを開けない場合（例: Claude.ai の VM にディスプレイがない、リモートサーバーにいる）は、ブラウザレビューアーを完全にスキップします。代わりに、結果を会話内で直接提示します。各テストケースについて、プロンプトと出力を示します。出力がユーザーが見る必要のあるファイル（.docx や .xlsx など）の場合は、ファイルシステムに保存し、どこにあるかを伝えて、ダウンロードして確認できるようにします。インラインでフィードバックを求めます:「これはどうですか？ 変更したい点はありますか？」

**ベンチマーク**: 定量的なベンチマーキングはスキップします — それはサブエージェントなしでは意味をなさない baseline 比較に依存しているからです。ユーザーからの定性的なフィードバックに焦点を当ててください。

**反復ループ**: 以前と同じです — スキルを改善し、テストケースを再実行し、フィードバックを求める — 途中にブラウザレビューアーがないだけです。ファイルシステムがあるなら、結果を反復ディレクトリに整理することは引き続きできます。

**description の最適化**: このセクションは `claude` CLI ツール（具体的には `claude -p`）が必要で、これは Claude Code でのみ利用可能です。Claude.ai にいる場合はスキップしてください。

**ブラインド比較**: サブエージェントが必要です。スキップしてください。

**パッケージ化**: `package_skill.py` スクリプトは、Python とファイルシステムがあればどこでも動作します。Claude.ai では実行でき、ユーザーは結果の `.skill` ファイルをダウンロードできます。

**既存スキルの更新**: ユーザーは新規作成ではなく、既存スキルの更新を求めているかもしれません。この場合:
- **元の名前を保持する。** スキルのディレクトリ名と frontmatter の `name` フィールドを確認し、それらを変更せずに使います。例: インストール済みスキルが `research-helper` なら、`research-helper.skill` を出力します（`research-helper-v2` ではなく）。
- **編集前に書き込み可能な場所にコピーする。** インストール済みのスキルパスは読み取り専用かもしれません。`/tmp/skill-name/` にコピーし、そこで編集し、コピーからパッケージ化します。
- **手動でパッケージ化する場合は、まず `/tmp/` にステージングする。** その後で出力ディレクトリにコピーします — 直接書き込むと権限の問題で失敗する可能性があります。

## Cowork 固有の指示

Cowork にいる場合、主に知っておくべきことは次のとおりです:

- サブエージェントがあるので、メインワークフロー（テストケースの並列起動、baseline の実行、採点など）はすべて機能します。（ただし、タイムアウトで深刻な問題が発生した場合は、テストプロンプトを並列ではなく直列で実行しても構いません。）
- ブラウザやディスプレイがないので、eval ビューアーを生成するときは、サーバーを起動する代わりに `--static <output_path>` を使ってスタンドアロンの HTML ファイルを書き出してください。その後、ユーザーがクリックしてブラウザで HTML を開けるリンクを提示してください。
- なぜかわかりませんが、Cowork のセットアップは、テスト実行後に Claude が eval ビューアーを生成するのを妨げる傾向があります。繰り返しになりますが、Cowork でも Claude Code でも、テスト実行後は、あなた自身がスキルを改訂して修正を試みる前に、人間がサンプルを見られるように、`generate_review.py` を使って（独自の小洒落た HTML コードを書かずに）常に eval ビューアーを生成してください。先に謝っておきますが、ここは大文字でいきます: 自分で入力を評価する*前に* EVAL ビューアーを生成してください。人間の前にできるだけ早くそれらを提示したいのです!
- フィードバックの仕組みが異なります: 実行中のサーバーがないため、ビューアーの「Submit All Reviews」ボタンは `feedback.json` をファイルとしてダウンロードします。そこからそれを読むことができます（最初にアクセスを要求しなければならないかもしれません）。
- パッケージ化は機能します — `package_skill.py` は Python とファイルシステムだけが必要です。
- description の最適化（`run_loop.py` / `run_eval.py`）は、ブラウザではなくサブプロセス経由で `claude -p` を使うため、Cowork でも問題なく動作するはずですが、スキルを完全に作り終え、ユーザーが良い状態だと同意するまで保存しておいてください。
- **既存スキルの更新**: ユーザーは新規作成ではなく、既存スキルの更新を求めているかもしれません。上記の claude.ai セクションの更新ガイダンスに従ってください。
