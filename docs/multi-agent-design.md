# マルチAgent構成 設計書

複数のAIエージェントを組み合わせて、ソフトウェア開発・技術調査・設計レビュー・CAE自動化などの
複雑なタスクを、品質・速度・コストのバランスを取りながら実行するための構成設計。

**実行基盤**: opencode（プライマリエージェント＋サブエージェント＋ファイルベース共有状態）

---

## 前提（仮定の明示）

設計を進めるにあたり、以下の前提を置く。異なる場合は読み替えること。

| 項目 | 仮定 |
|---|---|
| 実行基盤 | opencode。メイン＝プライマリエージェント、専門処理＝サブエージェント（`~/.config/opencode/agent/*.md`） |
| 並列実行 | opencodeの Task ツールで複数サブエージェントを同時起動できる |
| 共有状態 | プロジェクト内 `.multiagent/` ディレクトリのJSONファイル（Git管理可、人間も読める） |
| モデル | 具体名を特定せず「高性能／標準／高速」の3段階で抽象化。実モデルは後述の割り当て表に従い差し替える |
| 対象ドメイン | ソフトウェア開発・技術調査・設計レビュー・CAE（数値解析）自動化 |
| 相互参照 | パネル型ではAgent同士を事前に相互参照させない（独立案→Judgeが比較） |

---

## 1. 単独AgentかマルチAgentかの判定

Agentを増やすことは目的ではない。**まず単独で可能かを判定**し、必要ならマルチAgentへ。

**単独Agentで処理すべきタスク**（オーバーヘッドが得を上回る）

- 単一ファイル・単一関数の修正
- 既知のコマンド実行（ビルド・テスト・lint）
- 簡潔な質問への回答、調べもの（1〜2回の検索で済む）
- 小規模なドキュメント・設定ファイルの作成
- 会話的な反復作業（対話しながら1つのことを仕上げる）

**マルチAgentが有効なタスク**（分割・並列・独立検証に価値がある）

- 複数モジュールにまたがる実装
- 調査・設計・実装・テストを並行できる作業
- アーキテクチャ設計・技術選定・セキュリティ設計など**複数案の比較**が重要な判断
- CAE評価方法の検討（モデル化方針・境界条件・妥当性など複数観点）
- 長時間継続するプロジェクト（成果物の受け渡しが必要）
- 独立性の高い検証（実装とは別者によるレビュー・テスト）

**判定フロー（メインAgentの最初の一手）**

```
依頼を受ける
  └─ 単一ステップで完了し、独立性の検証や複数案比較が不要か？
       ├─ YES → 単独で処理（サブエージェントを起動しない）
       └─ NO  → マルチAgent。パターンを選ぶ（下記2）
```

## 2. 採用する構成パターンと理由

3パターンを組み合わせた**ハイブリッド構成**を採用する。タスク特性で選択する。

### 2.1 ルーター型（既定）

メインAgentが依頼を分析し、1つの専門Agentへ割り当てる。

- **適用**: 通常の調査、単一機能の実装、ドキュメント作成、バグ修正、定型的レビュー
- **理由**: 依存のない単発タスクでは、並列化や合議のオーバーヘッドが無駄。最短経路。

### 2.2 パネル＋ジャッジ型

複数Agentが同じ課題を独立に検討 → Judgeが比較・統合。

- **適用**: アーキテクチャ設計、技術選定、セキュリティ設計、CAE評価方法の検討、重要意思決定
- **理由**: 設計判断は「前提の違い」に結論が左右されやすい。独立案を先に出させることで、
  前提・利点・欠点・リスク・根拠を公平に比較でき、集団思考や早期収束を避けられる。
- **制約**: パネル同士は相互参照させない。Judgeは多数決でなく**前提・根拠・リスク・検証結果**で判定する。

### 2.3 共有メッセージボックス型

複数Agentが共通のタスク状態（`.multiagent/`）と成果物を参照しながら分担する。

- **適用**: 複数モジュール実装、調査→設計→実装→テストの並行、長期プロジェクト、成果物の受け渡し
- **理由**: 状態を中央の構造化ファイルに置くことで、Agent間の口頭引き継ぎ（自由な会話ログ）を避け、
  検証可能な成果物だけを受け渡せる。
- **制約**: 自由な会話ログを共有状態に**しない**。構造化された情報（契約・状態・成果物の場所・検証結果）だけを保存する。

## 3. Agent構成・役割・責任範囲

基本は4役。パネル型のときだけ Judge を追加する。

| Agent | 役割 | 責任範囲 | 変更権限 |
|---|---|---|---|
| メイン（プライマリ） | ユーザー対話、Agent選択、状態管理、統合、競合解消、最終回答 | 全体 | 全般（ただし設計判断の最終採否） |
| `planner` | 要求整理、タスク分割、入出力契約・完了条件の定義 | 計画・契約 | 読み取り中心（成果物は計画） |
| `implementer` | コード・設定・図・文書などの成果物作成 | 作成・変更 | 指定されたファイルのみ |
| `domain-reviewer` | 専門領域・設計妥当性・前提条件の確認 | レビュー | 読み取りのみ |
| `verifier` | テスト、差分確認、要件適合性、再現性の検証 | 検証 | 読み取り＋コマンド実行 |
| `judge`（パネル時のみ） | 独立案の比較・統合・推奨の提示 | 合議 | 読み取りのみ |
| `vision` | 画像の読解・解析（スクリーンショット・図・設計図・ロゴなど） | 画像読解 | 読み取りのみ |
| `imagine` | 画像の生成（イラスト・ロゴ・UIモック・図解など） | 画像生成 | 画像出力 |

**基本ルール**: メインAgentはユーザーとの対話と最終判断に責任を持ち、実際の作成・検証はサブエージェントに委譲する。
「重要な判断は実装担当とは別のAgentがレビューする」（実装=implementer、レビュー=domain-reviewer/verifier）。

## 4. 依存関係と実行順序

```
ルーター型（単発）:
  planner(任意) → implementer → verifier → [domain-reviewer] → メイン統合

パネル＋ジャッジ型:
  planner → (A案) (B案) (C案)  …並列・独立…
                  ↓
                judge → メイン採否 → (採択後) implementer → verifier

共有メッセージボックス型:
  planner → タスク分割(依存グラフ) → 依存のないタスクを並列実行
  → 成果物を .multiagent/ に登録 → 依存解消された次タスクを実行 → verifier → メイン統合
```

依存関係は `planner` が `dependencies` として定義し、メインAgentがそれに従って実行順序を制御する。

---

## 5. 並列実行できるタスク

- **依存関係がないタスク**: 異なるモジュール・ファイルの実装、独立した調査、独立したテスト
- **パネル型の独立案**: 同じ課題への複数案（互いに参照しない）
- **実装と直交する検証準備**: 実装中に、テスト方針の策定（verifier）や設計レビュー（domain-reviewer）を先行

**並列してはいけないタスク**: 同じファイル・同じ設計判断を同時更新するタスク（担当範囲を事前に明確化）。

## 6. 各Agentへ渡すプロンプト

メインAgentがTaskツールで起動する際、必ず以下を明示する（実行ルール4）。

```
【目的】
【入力】…（読み込むファイル・参照・前提）
【出力形式】…（ファイルパス／スキーマ／レポート形式）
【完了条件】…（何をもって完了とするか）
【変更可能範囲】…（編集してよいファイル、してはいけないファイル）
【制約】…（利用技術、禁止事項、独立検討の指示）
```

各サブエージェントの固定プロンプト本体は `config/opencode/agent/*.md` に定義済み。
メインAgentは上記の可変部分を毎回付与する。

## 7. 共有状態のデータ構造

保存場所: `.multiagent/`（プロジェクトルート。Git管理推奨）

```
.multiagent/
├── registry.json            # タスク索引（メインAgentのみが書き換え）
├── tasks/<task_id>.json     # タスク契約＋状態（1タスク1ファイル）
└── artifacts/<task_id>/     # 検証可能な成果物（コード・レポート・図・検証結果）
```

### registry.json

```jsonc
{
  "version": 1,
  "tasks": {
    "T-20260905-001": {
      "title": "…",
      "status": "in_progress",
      "assignee": "implementer",
      "dependencies": [],
      "updated_at": "2026-09-05T00:00:00Z"
    }
  }
}
```

### tasks/<task_id>.json（タスク契約）

```jsonc
{
  "task_id": "T-20260905-001",
  "objective": "…",
  "pattern": "router",              // router | panel | messagebox
  "assignee": ["planner"],          // 現在の担当（複数可）
  "status": "pending",              // 後述の状態遷移
  "dependencies": ["T-…"],
  "input_contract": {
    "paths": ["src/…"],
    "refs": ["docs/…"],
    "context": "前提・制約の説明"
  },
  "output_contract": {
    "files": ["out/…"],
    "format": "json|md|code|…",
    "schema": "スキーマ参照または説明"
  },
  "acceptance_criteria": ["…"],
  "decisions": [
    { "id": "D1", "decision": "…", "rationale": "…", "by": "judge", "at": "…" }
  ],
  "unresolved_questions": ["…"],
  "changed_files": ["src/…"],
  "verification_results": [
    { "check": "単体テスト", "result": "pass", "evidence": "artifacts/T-…/test.log", "at": "…" }
  ],
  "artifact_locations": ["artifacts/T-…/…"]
}
```

### 状態遷移

```
pending → assigned → in_progress → review → completed
            ↑                        │
            │            rework_required
            │                        │
            └────────── blocked ─────┘
                        cancelled
```

- `pending`: 計画済み・未着手
- `assigned`: 担当Agent決定
- `in_progress`: 実行中
- `review`: 成果物が出たのでレビュー中
- `completed`: 完了条件を満たし検証済み
- `blocked`: 依存未解決・入力不足で停止
- `rework_required`: レビューで不合格、差し戻し
- `cancelled`: 不要になった

## 8. 成果物の統合方法

- Agentの**回答ではなく、検証可能な成果物**（ファイル・テスト結果・出典・計算結果）を受け渡す（実行ルール5）。
- サブエージェントは成果物を `artifacts/<task_id>/` または指定されたリポジトリ内パスに書き出し、最終メッセージで
  「成果物パス＋検証結果＋未解決の疑問」を報告する。
- メインAgentは報告に基づき `registry.json` と `tasks/<task_id>.json` を更新し、成果物を本体（src/等）へ統合する。
- 複数案は Judge が比較表（前提・利点・欠点・リスク・根拠）で統合し、メインAgentが最終採否を決める。

---

## 9. レビューおよび検証方法

- **設計判断**: `domain-reviewer` が専門観点で、実装とは独立にレビュー。
- **成果物**: `verifier` が「テスト・差分・要件適合性・再現性」を確認し、`verification_results` に記録。
- **合議**: `judge` が複数案を比較（多数決ではなく根拠比較）。
- レビューで不合格 → `rework_required` で実装者へ差し戻し。再実装→再検証を繰り返す。
- メインAgentは最終的に `acceptance_criteria` をすべて満たすことを確認して `completed` にする。

## 10. 競合・失敗・暴走への対策

| リスク | 対策 |
|---|---|
| 同じファイルの同時更新 | 担当範囲・編集可能ファイルを起動時に明示。1タスク1ファイル原則。状態はメインAgentだけが書き換える |
| 前提の食い違い | 入力契約に前提・制約を明記。domain-reviewerが前提の妥当性を確認 |
| 意見対立 | 多数決にしない。Judgeが前提・根拠・リスク・検証結果を列挙し、メインAgentが根拠で採否 |
| 依存の循環 | plannerが依存グラフを作る際に循環を検出。循環があれば計画を作り直す |
| 失敗・ハルシネーション | 受け渡しを成果物（ファイル・出典・計算結果）に限定。verifierが再現性・要件適合性を独立検証 |
| 暴走（際限なくAgentを増やす） | 実行ルール10。通信コスト＞削減効果なら単独Agentへ戻す。パネル数は原則2〜3、最大5 |
| 完了条件の曖昧さ | plannerが完了条件を事前定義。満たさない限りcompletedにしない |
| 状態の不整合 | 状態はメインAgentのみ更新。サブエージェントは読み取り専用 |

## 11. 使用モデルの割り当て方

モデルは具体名を特定せず3段階で抽象化する。実際のIDはユーザーのプロバイダに合わせて
`~/.config/opencode/opencode.jsonc` の `agent.<name>.model` で差し替える。

| 段階 | 用途 | 割り当て |
|---|---|---|
| 高性能 | 要件整理・契約定義・最終判定・重要設計レビュー | メイン（既定）、`planner`（複雑時）、`judge`、`domain-reviewer`（重要判断） |
| 標準 | 実装・検証・一般調査 | `implementer`、`verifier`、`domain-reviewer`（通常） |
| 高速 | 定型・軽微・単純作業 | ルーターの単純振り分け、単一ファイル修正、要約、軽微レビュー |
| vision（画像読解） | スクリーンショット・図・設計図の解析 | `vision`（`opencode-go/deepseek-v4-flash-vision-exp`） |
| 画像生成 | イラスト・ロゴ・UIモック・図解の生成 | `imagine`（`openai/gpt-5.4-image-2` 等） |

**原則（実行ルール9）**: 高性能モデルを常用しない。通常作業は標準・高速モデル、重要設計と最終判定のみ高性能。

設定例（差し替え前提。実在するモデルIDに置き換えること）:

```jsonc
// ~/.config/opencode/opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "planner":          { "model": "<高性能モデルID>" },
    "judge":            { "model": "<高性能モデルID>" },
    "implementer":      { "model": "<標準モデルID>" },
    "verifier":         { "model": "<標準モデルID>" },
    "domain-reviewer":  { "model": "<標準モデルID>" }
  }
}
```

※ `model` を未指定にするとセッション既定モデルを継承する（現実装は未指定＝継承）。

## 12. トークン量・処理時間・APIコストを抑える方法

1. **単独優先**: まず単独Agentで処理できるか判定（最もコストを下げる）。
2. **モデル段階を使い分け**: 通常作業は標準・高速モデル、重要判断のみ高性能。
3. **成果物の受け渡し**: 長文の回答でなく、ファイルパスと要約だけを返す（会話ログを共有状態にしない）。
4. **入力契約の限定**: 必要なファイルだけを渡し、リポジトリ全体を読ませない。
5. **並列化**: 依存のないタスクを並列実行して待ち時間（処理時間）を短縮。ただし無理な並列化は通信コスト増。
6. **パネル数の抑制**: 原則2〜3案。多いほどコストは線形に増える。
7. **状態の最小化**: 共有状態は構造化フィールドのみ。自由な会話ログを保存しない。
8. **収束条件の明確化**: 完了条件を事前定義し、無限の反復（再レビュー・再実装）を防ぐ。
9. **実行ルール10の適用**: 通信コスト＞削減効果なら単独に戻す。

## 13. 最小構成から段階的に拡張するロードマップ

| 段階 | 構成 | 目的 |
|---|---|---|
| 0 | 単独Agentのみ（現状） | ベースライン。単独で十分なタスクはこのまま |
| 1 | ルーター型：`implementer` ＋ `verifier` を追加 | 単一機能実装＋独立検証。最小のマルチAgent |
| 2 | `planner` を追加 | 複数ステップの計画と契約定義。共有状態導入 |
| 3 | `domain-reviewer` を追加 | 設計・専門領域の独立レビュー（CAE等） |
| 4 | パネル＋ジャッジ（`judge`）を追加 | 重要意思決定の複数案比較 |
| 5 | 共有メッセージボックス運用＋チューニング | 長期プロジェクト、モデル段階の最適化、ルール見直し |

各段階で「単独で良かったか」を振り返り、効果が薄いAgentは使わない（実行ルール10）。
